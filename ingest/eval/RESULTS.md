# Entity resolution 測試 v1

> ⚠️ **呢份係第一輪結果，而且同 v2 有一樣嘅限制**（Claude 判斷、描述截斷、
> 部分店名被補全）。讀之前先睇 [`RESULTS_v2.md`](RESULTS_v2.md) 頂部嘅覆核。

20 篇真實 YouTube 食評（12 HK / 8 JP），標題 + 描述，**冇字幕**。
抽取用 `ingest/prompt.md` v1，配對用 Nominatim（`ingest/match.py`）。

## 結果

| | 抽到 mention | 配到 POI | **Claude 判斷正確** | 端到端 |
|---|---|---|---|---|
| HK | 31 | 15 | 13 | **42%** |
| JP | 48 | 24 | 23 | **48%** |
| 合計 | 79 | 39 | 36 | **46%** |

20 篇入面 **5 篇（25%）零收穫**。原因各有不同，見 v2 覆核第 5 點。

## 三個推翻咗原本假設嘅發現

**一、日本唔係難嗰邊，香港先係。**

原本估 HK 85% / JP 70%。實際係 HK 42% / JP 48% —— 數值同**次序**都錯。

可能嘅原因（未驗證）：日文店名係高辨識度專有名詞（`とんぼや`、`壽々喜園`、`おいもやさん興伸`），而且東京嘅 OSM 覆蓋極好。香港店名反而多數係通名（`水記`、`寶樹堂`、`夜嗜野`），細舖喺 OSM 嘅覆蓋亦差好多。

漢字/かな/羅馬字變體我原本當成風險，實際上 Nominatim 食得好順：`丸豊 → Marutoyo`、`山長 → Yamacho`、`浅草もんじゃころっけ → 浅草もんじゃコロッケ` 全部配啱。

**二、樽頸唔喺抽取，喺配對。**

79 條 mention 抽得出，得 39 條配到嘢。抽取（尤其係合集片嘅時間軸列表）表現遠好過預期 —— 描述入面通常有完整店名同地址。

**三、錯配會靜靜咁毒害個圖譜。**

| 抽到 | 配到 | OSM 類別 |
|---|---|---|
| 夜嗜野 | 基督教香港信義會尊聖堂 | `amenity/place_of_worship` |
| 寶樹堂 | 保良局唐乃勤初中書院 | `amenity/school` |
| and TOKYO | RIGOLETTO WINE AND BAR | `amenity/restaurant` |

頭兩個**淨係靠 OSM 類別就擋得晒** —— 教堂同學校唔係餐廳。呢個係一行 code 嘅事，做完命中嘅精確度由 92% 升到 97%。

第三個擋唔到（真係餐廳，但係錯嗰間），要靠距離同名稱相似度。

## 46% 係下限，唔係上限

而家個 matcher 好原始：一個 query（`店名 + 地區 + 城市` 串埋），冇 fallback。已知可以改善嘅位：

1. **類別過濾** —— 即刻擋走兩個錯配
2. **多重 query 策略** —— 淨用店名 + bbox、去掉地區前綴（`浅草メンチ` → `メンチ`）、羅馬字變體
3. **Tabelog 連結** —— 第 16 篇描述直接俾咗 8 條 tabelog URL，即係免費嘅精確 ID。日本食評片好常見
4. **字幕** —— 解嗰 25% 零收穫嘅片
5. **試 Overture** —— 可能覆蓋闊過 OSM，未驗證

## 對產品嘅影響

- **MVP 唔使縮返做香港獨市。** 日本一樣做得，甚至順啲。
- **`match_confidence` 要由 matcher 出，唔可以只靠抽取器。** 而家 schema 入面呢個欄位由 LLM 填，但 LLM 只知「呢串字似唔似店名」，唔知「配到邊間」。要分成兩個數。
- **人手覆核佇列係必需品，唔係 nice-to-have。** 一半 mention 配唔到，`edit_proposal` 嗰套眾包機制而家係主線功能。

## 呢個測試嘅限制

- 只用標題 + 描述，冇字幕 —— 真 pipeline 會有
- YouTube only，冇 IG caption（短、多 emoji、多 hashtag，難好多）
- 抽取由 Claude 喺對話入面跑，唔係 API 自動跑（本機冇 API key），而且只睇咗描述頭 1100 字
- Nominatim 係 Overture 嘅 proxy，唔係最終要用嗰個資料源
